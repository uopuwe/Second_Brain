# Recommendations

## Purpose

This document contains preferred practices.
They guide judgment when the user leaves details open.
Mandatory rules are in [mandatory_rules.md](mandatory_rules.md).

## General Recommendations

- Prefer updating canonical notes over creating parallel notes.
- Prefer concise durable synthesis over long pasted content.
- Prefer relative Markdown links over ambiguous references.
- Prefer source-backed statements over confident wording.
- Prefer one clear note per concept over many tiny fragments.
- Prefer links over duplicated explanations.
- Prefer examples with units over abstract definitions.
- Prefer explicit open questions over hidden uncertainty.

## Engineering Recommendations

- Start technical notes from system impact.
- Move from system to architecture to circuit to equation to debug.
- Include one realistic failure mode for important notes.
- Include one design tradeoff for important notes.
- Keep exact standards values out unless sourced.
- Use Python examples only when they add reproducible value.

## Writing Recommendations

- Use short paragraphs.
- Use headings as navigation.
- Use tables only when they improve comparison.
- Use text diagrams for signal chains.
- Avoid decorative Markdown.
- Avoid heavy plugin-specific Obsidian syntax.

## Knowledge Architecture Recommendations

- Route by primary purpose, not by every keyword.
- Keep paper summaries source-specific.
- Keep interview answers linked to deeper notes.
- Keep career strategy separate from reusable technical fundamentals.
- Keep duplicate folders non-canonical until reviewed.

## Automation Opportunities

Future agents may add tooling for:

- Frontmatter validation.
- Broken link checking.
- Source-provenance scanning.
- Duplicate note detection.
- Formula-definition checks.
- Standards-claim detection.
- Index freshness reports.
- Vault health dashboards.

Automation should suggest changes.
It should not silently rewrite or delete durable knowledge.
